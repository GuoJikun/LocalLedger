# 净账（LocalLedger）— 项目规划

> 本地运行、离线优先的记账软件，通过导入支付宝 / 微信账单生成流水与统计。
> 跨平台（Windows / macOS / Linux），后续可选支持局域网内多设备数据同步。

---

## 一、产品定位

| 项 | 内容 |
|---|---|
| 名称 | 净账（英文项目名 `LocalLedger`） |
| 形态 | 跨平台桌面应用（Windows / macOS / Linux），无需注册、默认离线 |
| 核心卖点 | 数据只留在自己电脑；不上传、不埋点、无账号体系 |
| 数据来源 | 支付宝 / 微信导出的 CSV 账单，以及少量手工录入 |
| 离线优先 | 默认完全离线；局域网同步为后续可选能力 |

设计原则：**本地文件是唯一数据源（Source of Truth）**，同步只是"在设备间搬运变更"，不改变核心业务逻辑。

## 二、功能范围

### MVP（V0.1 ~ V0.5）

- [ ] 导入支付宝 CSV 账单（自动识别编码与表头、去重）
- [ ] 导入微信 CSV 账单（同上）
- [ ] 交易流水：列表、搜索、按时间/类型/分类/金额筛选
- [ ] 分类管理：自动分类规则 + 手动改分类
- [ ] 统计：月度收支、分类占比、简单趋势图
- [ ] 手工录入 / 编辑 / 删除单笔交易
- [ ] 本地备份与导出（数据库文件备份、CSV 导出）
- [ ] 导入错误行提示（哪一行、什么原因）

### 后续（V1.x）

- [ ] 局域网同步：设备发现、增量同步、冲突处理
- [ ] 多账本（个人 / 家庭分开）
- [ ] 预算与超支提醒
- [ ] 标签、备注、周期账单识别
- [ ] 账单规则自定义（用户可配置平台字段映射）

## 三、技术选型

沿用熟悉的 Rust + Tauri + Vue 技术栈，避免引入不必要的依赖。

| 层 | 选型 | 理由 |
|---|---|---|
| 桌面壳 | Tauri 2 | 一套代码覆盖 Windows / macOS / Linux；包体小、Rust 后端可控 |
| 前端 | Vue 3 + Vite + TypeScript | 与既有技术栈一致 |
| 后端 | Rust（tokio） | 文件/CSV/SQLite 处理都在 Rust 侧 |
| 数据库 | SQLite（`rusqlite`，后续可换 `sqlx`） | 单文件、零配置、天然适合本地与备份 |
| CSV 解析 | `csv` crate + `encoding_rs` | 处理 GBK / UTF-8 BOM 等编码差异 |
| 时间 | `chrono` | 时间解析与时区处理 |
| 序列化 | `serde` | IPC 与配置序列化 |
| 图表 | ECharts（前端） | 覆盖统计需求，生态成熟 |
| 测试 | Rust 内置测试 + 前端 Vitest | 解析器必须有测试样例保障 |

约束：**克制新增依赖**，优先复用依赖树已有库；金额一律用整数"分"存储，杜绝浮点误差。

## 四、架构设计（为局域网同步预留）

分层结构，UI 不直接碰数据库：

```
Vue 前端 ──Tauri IPC──> 命令层（commands）
                          │
                          ▼
                       领域层（交易 / 分类 / 统计 / 导入）
                          │
                          ▼
                       存储层（Repository trait + SQLite 实现）
                          │
                          ▼
                      本地 SQLite 文件
```

### 同步预留的关键设计（MVP 就要落实）

1. **业务表统一带同步元数据**：`updated_at`、`device_id`、`version`、`deleted`（软删除）。
2. **独立变更日志表 `sync_changes`**：每次增删改追加一条记录（实体类型、实体 ID、操作类型、序列号）。局域网同步只消费这张表做增量同步，无需改动业务代码。
3. **交易唯一键 `source + external_id`**：支付宝交易号 / 微信交易单号天然去重，重复导入不会产生脏数据。
4. **Repository trait 抽象**：业务逻辑依赖 trait 而非具体实现，未来同步服务作为独立模块接入。
5. **设备标识 `devices` 表**：为冲突解决（LWW 需要区分设备）做准备。

> MVP 阶段不实现同步，但上述字段和表**现在就建好**，避免将来大改数据结构。

### 局域网同步方案（V1.x 实施）

- **发现**：mDNS 自动发现（macOS 用原生 Bonjour；Linux 依赖 Avahi；Windows 需 Bonjour 或纯 Rust 实现），并始终提供手动输入 IP 兜底，避免平台差异阻塞同步。
- **传输**：一台设备作为主节点提供轻量 HTTP API（`axum`），其余设备拉取/推送变更。
- **增量**：基于 `sync_changes.seq` 游标，只传变化部分。
- **冲突**：默认 LWW（比较 `updated_at` + `device_id`），冲突时保留双方版本并提示用户选择。
- **安全**：局域网内先不加密；后续可加 TLS 或端到端加密。

## 五、核心数据模型

| 表 | 关键字段 |
|---|---|
| `accounts` | id, name, type, created_at |
| `transactions` | id, account_id, source, external_id, kind(income/expense/transfer), amount(分), counterparty, category_id, note, happened_at, payment_method, status, raw_data, created_at, updated_at, device_id, version, deleted |
| `categories` | id, name, parent_id, icon, color, sort_order |
| `category_rules` | id, keyword, match_field, category_id, priority |
| `sync_changes` | seq, entity_type, entity_id, op, payload, created_at, device_id |
| `devices` | id, name, last_seen_at |
| `meta` | key, value（schema 版本、最后同步游标等） |

约束：`UNIQUE(source, external_id)` 保证导入幂等。

## 六、账单导入设计

### 通用流程

```
读文件 → 检测编码 → 跳过头部说明 → 识别列映射
      → 逐行解析 → 金额标准化（元→分）→ 去重
      → 自动分类 → 写入数据库 → 返回成功/失败行统计
```

### 支付宝 CSV 要点

- 编码通常为 **GBK**，需转 UTF-8。
- 文件头部有元信息行（账号、账单周期），需跳过。
- 关键列：交易号、交易时间、交易分类、交易对方、商品说明、收/支、金额、支付方式、交易状态。
- 状态非"交易成功"的记录需标记或过滤。

### 微信 CSV 要点

- 编码通常为 **UTF-8 with BOM**。
- 头部有说明行，需跳过。
- 关键列：交易时间、交易类型、交易对方、商品、收/支、金额(元)、支付方式、当前状态、交易单号。
- 微信账单中"转账/红包/退款"等特殊类型需单独归类处理。

### 健壮性

- 平台字段可能调整：列映射做成可配置规则，解析器与字段映射解耦。
- 每个平台准备真实脱敏样例 CSV 作为测试夹具，解析器改动必跑测试。
- 解析失败的行汇总反馈给用户，不静默丢弃。

## 七、开发阶段

| 阶段 | 目标 | 交付 |
|---|---|---|
| 0 | 脚手架 | Tauri + Vue + SQLite 跑通，基础窗口与布局 |
| 1 | 数据层 | 数据库迁移、Repository、交易/分类 CRUD |
| 2 | 导入解析 | 支付宝/微信解析器 + 真实样例测试 + 导入 UI |
| 3 | 流水管理 | 列表、搜索筛选、手动改分类、编辑删除 |
| 4 | 统计 | 月度收支、分类占比、趋势图 |
| 5 | 打磨 | 备份导出、错误提示、打包安装器 → **MVP 完成** |
| 6 | 局域网同步 | 变更日志消费、设备发现、增量同步、冲突处理 |

每个阶段结束都要跑：格式化、clippy、Rust 测试、前端构建。改动同步更新文档与变更记录。

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 账单格式/编码变化 | 列映射配置化；每个平台维护脱敏样例 + 回归测试 |
| 中文编码 GBK / BOM | `encoding_rs` 自动识别，必要时让用户手动选编码 |
| 金额精度 | 整数"分"存储，展示时才格式化 |
| 重复导入 | `source + external_id` 唯一约束，幂等导入 |
| 同步冲突 | 提前埋好元数据与变更日志；默认 LWW，冲突保留双方版本人工选择 |
| 隐私承诺 | 默认离线、无埋点、无账号；网络访问需用户显式开启 |
| 跨平台差异 | 路径统一用 `app_data_dir`；文件选择用 Tauri dialog；时间统一存 UTC；CI 一开始覆盖三平台 |
| 平台打包签名 | macOS 需开发者签名与公证；Windows 可选代码签名；先保证功能正确，再处理签名 |
