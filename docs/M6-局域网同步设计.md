# 净账（LocalLedger）— M6 局域网同步设计方案

> 状态：**设计待评审，尚未实现**。
> 依据：`规划.md` 第四节「架构设计（为局域网同步预留）」、`计划.md` M6 任务与验收标准。
> 场景：自己的多台设备同步同一个账本，默认按**对等同步**设计，无中心节点。

---

## 一、目标与非目标

### 目标

1. 两台（及以上）设备在同一局域网内双向同步账本数据。
2. 基于 `sync_changes.seq` 做增量同步，断网重连后只传变化部分。
3. 冲突默认按 LWW 解决，且**冲突双方版本都保留**，由用户选择。
4. 网络访问必须用户显式开启；默认完全离线。
5. 前端只消费命令层，不直接访问同步模块或数据库。

### 非目标（本期不做）

- 公网同步、账号体系、端到端加密/TLS（后续可选）。
- 多账本隔离（MVP 单账本，数据结构已预留）。
- 自动解决所有冲突（只给默认策略 + 人工选择入口）。
- files / 图片附件同步。

## 二、总体架构

```
Vue 前端
   │ Tauri IPC
   ▼
commands/sync.rs ── State<AppState> ──► sync::Service（编排）
                                          │
              ┌───────────────────────────┼───────────────────────────┐
              ▼                           ▼                           ▼
        sync::discovery            sync::transport              sync::conflict
        mDNS + 手动 IP             axum server / reqwest         LWW + 双版本保留
              │                           │                           │
              └───────────────────────────┼───────────────────────────┘
                                          ▼
                              Repository trait / SQLite
                              sync_changes、sync_applied、
                              sync_peers、sync_conflicts、meta
```

设计原则：**同步只是「在设备间搬运变更」**，不改动已有业务代码路径。M1 已埋好的 `updated_at / device_id / version / deleted` 与 `sync_changes` 直接复用；M6 只新增同步专属表与模块。

## 三、关键设计决策

### 3.1 变更身份：`(device_id, seq)` 复合键

`sync_changes.seq` 是每台设备本地自增的，不同设备的 `seq=5` 不是同一个变更。因此：

- 远端变更的唯一身份 = `(origin_device_id, origin_seq)`。
- 本地已应用的远端变更记录在 `sync_applied`，避免重复应用与回声循环。
- 对端游标 `sync_peers.last_remote_seq` 表示「我从该设备消费到的最大 seq」。

### 3.2 应用远端变更不能产生本地变更日志

如果把远端变更当作普通 CRUD 写回，会追加一条本设备的 `sync_changes`，导致两端无限互推。
解决：Repository 新增专用方法 `apply_remote_change`，它：

1. 用远端携带的 `updated_at / device_id / version` 原样写入实体；
2. **不**追加本地 `sync_changes`；
3. 写入 `sync_applied(origin_device_id, origin_seq)` 标记已消费。

只有用户主动编辑（含冲突解决）才走普通 Repository 方法，生成新的本地变更。

### 3.3 LWW 与冲突保留

比较规则：`updated_at` 大者胜；完全相同则 `device_id` 字典序大者胜（确定性 tie-break）。

- 远端胜：应用远端版本；若本地版本与远端 payload 不同，把**本地版本**存入 `sync_conflicts`。
- 本地胜：保留本地版本；把**远端版本**存入 `sync_conflicts`。
- 冲突记录包含双方完整 payload，用户可选择「用本地 / 用远端」，选择结果走普通 Repository 写入（生成新变更广播给对端），并把记录标记为已解决。

> 说明：不做向量时钟/版本向量，依赖设备时钟。要求设备开启 NTP；tie-break 保证时钟相近时结论一致。时钟大幅偏差属于已知限制，写入风险清单。

### 3.4 对等拓扑

任意设备既可是客户端也可是服务端：

- 每台开启同步的设备运行一个 axum HTTP 服务（默认端口 `17342`，可配置）。
- 用户手动添加对端 `host:port`，或通过 mDNS 发现同网段设备。
- 同步时对端角色对等：本端拉取 + 本端推送，不区分主从。

## 四、数据模型增补（迁移 003）

> 不修改 M1/M2 已建立的表结构，只新增同步专属表。

```sql
CREATE TABLE IF NOT EXISTS sync_peers (
    id              TEXT PRIMARY KEY,              -- uuid
    device_id       TEXT NOT NULL UNIQUE,          -- 对端设备 ID
    name            TEXT NOT NULL,
    address         TEXT NOT NULL,                 -- ip:port 或 host:port
    last_remote_seq INTEGER NOT NULL DEFAULT 0,    -- 从对端消费到的最大 seq
    last_sent_seq   INTEGER NOT NULL DEFAULT 0,    -- 推送给对端的本地最大 seq
    last_sync_at    TEXT,
    status          TEXT NOT NULL DEFAULT 'idle',  -- idle/connecting/online/error
    error           TEXT,
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS sync_applied (
    origin_device_id TEXT NOT NULL,
    origin_seq       INTEGER NOT NULL,
    applied_at       TEXT NOT NULL,
    PRIMARY KEY (origin_device_id, origin_seq)
);

CREATE TABLE IF NOT EXISTS sync_conflicts (
    id            TEXT PRIMARY KEY,
    entity_type   TEXT NOT NULL,
    entity_id     TEXT NOT NULL,
    local_payload TEXT,                            -- 本地版本完整 JSON
    remote_payload TEXT,                           -- 远端版本完整 JSON
    origin_device_id TEXT NOT NULL,
    detected_at   TEXT NOT NULL,
    resolved      INTEGER NOT NULL DEFAULT 0,
    resolution    TEXT                             -- local / remote
);

-- meta 新增 key：sync_enabled、sync_port、sync_peer_token（可选）
```

索引：`sync_applied(origin_device_id)`、`sync_conflicts(resolved, detected_at)`。

`sync_changes` 表结构保持不变；payload 字段已是完整实体 JSON，可直接用于冲突展示与回放。

## 五、HTTP 协议（axum）

绑定：`0.0.0.0:<sync_port>`；仅在内网监听，且仅在用户开启同步后启动。

| 方法 | 路径 | 请求 | 响应 | 说明 |
|---|---|---|---|---|
| GET | `/sync/info` | — | `{device_id, device_name, app_version, schema_version, cursor, timestamp}` | 握手/探活，用于确认对端 |
| GET | `/sync/changes?since=&limit=` | — | `{changes: SyncChange[], next_cursor}` | 拉取本端变更日志（增量） |
| POST | `/sync/changes` | `{origin_device_id, changes: SyncChange[]}` | `{applied, duplicates, conflicts, max_seq}` | 接收远端变更并应用 |
| GET | `/sync/health` | — | `ok` | 状态检测 |

约定：

- `since` 为对端已消费的 `sync_changes.seq`，`limit` 默认 500、上限 1000。
- 变更数组按 `seq` 升序返回；`next_cursor` = 最后一条的 seq。
- POST 幂等：重复 `(origin_device_id, origin_seq)` 直接计入 `duplicates` 并跳过。
- 所有请求/响应 JSON 使用 serde；字段与 Tauri 命令共用 `domain` 结构体。
- 可选共享令牌：请求头 `X-LocalLedger-Token`，对端校验；MVP 默认空（不启用）。

## 六、同步流程

### 6.1 启动

1. 用户在「设置 → 同步」打开总开关（显式同意）。
2. 根据 `meta.sync_port` 启动 axum 服务；失败则提示端口占用。
3. 启动 mDNS 广播与浏览（`_local-ledger._tcp.local.`，TXT 携带 `device_id`、`port`、`ver`）。
4. 前端展示本机设备 ID、端口、发现到的设备与手动添加入口。

### 6.2 单次同步（对每个 peer）

```
1. GET  /sync/info                     → 确认对端在线、schema 兼容
2. GET  /sync/changes?since=last_remote_seq
   → 对每条变更：
        a. (origin, seq) 已在 sync_applied？跳过
        b. 冲突检测（LWW）→ 必要时写 sync_conflicts
        c. apply_remote_change（不生成本地变更）
        d. 写 sync_applied，更新 last_remote_seq
3. GET  本地 sync_changes WHERE seq > last_sent_seq
   → POST /sync/changes 给对端
   → 更新 last_sent_seq
4. 更新 peer.last_sync_at、status=online
```

失败时记录 `peer.error`、`status=error`；不回滚已成功应用的远端变更（增量可重复执行且幂等）。

### 6.3 触发时机

- 手动「立即同步」按钮。
- 定时轮询（默认 30s，可配置）。
- 新增/编辑/导入交易后触发一次（防抖 5s）。
- 网络恢复事件（mDNS 重新发现 peer）触发。

### 6.4 冲突处理 UI

「设置 → 同步 → 冲突」列表展示实体类型、实体名、双方金额/时间/device_id 摘要；用户选「保留本地 / 采用远端」后：

1. 用选中 payload 走普通 Repository 更新；
2. 标记 `sync_conflicts.resolved = 1` 并记录 resolution；
3. 下一次同步把该结果广播出去。

|---|---|

## 八、安全与隐私

- 默认关闭；只有用户显式开启才监听端口、才发起网络请求。
- 仅监听局域网地址；不尝试公网穿透，不在后台上传任何数据。
- 可选共享令牌（头 `X-LocalLedger-Token`），同一用户设备间配置一致即可。
- MVP 不加密，符合规划「局域网内先不加密」；UI 明确提示风险。
- `app_data_dir` 中数据库文件权限由操作系统默认保护。

## 十、验收标准（对齐计划 M6）

- 两台不同操作系统设备在局域网内**双向**同步：任一端新增/编辑/删除，另一端可见。
- 断网期间两端各自修改，重连后增量同步正确，不重复、不丢数据。
- 冲突不丢数据：`sync_conflicts` 保留双方版本，UI 可选择，选择后广播生效。
- 重复导入/重复推送幂等；`sync_applied` 阻止回声循环。
- 关闭同步后无任何网络监听与请求。

## 十一、风险与开放问题

| 风险 | 对策 / 待确认 |
|---|---|
| mDNS 跨平台差异（Windows 需 Bonjour 等） | 优先纯 Rust `mdns-sd`；**始终保留手动 IP 兜底**（文档硬要求） |
| 设备时钟偏差影响 LWW | 要求 NTP；tie-break 用 device_id；偏差大时以人工冲突解决兜底 |
| 并发写入同一 SQLite 文件 | 所有访问经 `AppState.conn` 的 Mutex；HTTP handler 与命令共用同一连接 |
| 变更日志膨胀 | `limit` 分页 + `last_sent_seq` 游标；后续可加归档/压缩 |
| 端口占用 / 防火墙 | UI 显示明确错误；允许自定义端口；手动 IP 模式需放行端口 |
| 隐私承诺 | 默认关闭；UI 明示「仅在同步开启时产生局域网流量」 |

**待确认事项**：

1. 同步开关默认关闭、端口默认 `17342` 是否可接受？
2. 是否需要可选的共享令牌（建议做，成本低）？
3. mDNS 服务类型名 `_local-ledger._tcp.local.` 是否确定？
4. 冲突保留期限：是否需要定期清理已解决冲突（建议保留 90 天）？
5. 是否需要在同步前要求两端 `schema_version` 完全一致（建议一致才能同步）？
